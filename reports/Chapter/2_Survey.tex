This chapter presents a comprehensive survey of the requirements for the ShieldX system. It begins by examining the current landscape of DoH-based malware detection and existing security solutions, then derives the functional and non-functional requirements that guide the system design. The use case model is presented to capture the interactions between users and the system.

\section{Status survey}
\label{section:2.1}

\subsection{Existing Solutions for DoH-based Malware Detection}

The detection of malware communication over DNS-over-HTTPS has attracted significant research interest in recent years. The CIC-DoHBrw-2020 dataset, published by the Canadian Institute for Cybersecurity (CIC), has become a benchmark for evaluating DoH traffic classification approaches. This dataset comprises over 500,000 labeled network flows with 28 statistical features, covering both benign and malicious DoH traffic scenarios.

Several machine learning approaches have been proposed for classifying DoH traffic:
\begin{itemize}
    \item MontazeriShatoori et al. \cite{montazeri2020doh} introduced the CIC-DoHBrw-2020 dataset and evaluated multiple classifiers including Random Forest, K-Nearest Neighbors, and Neural Networks, achieving over 99\% accuracy in controlled experiments.
    \item Singh and Kaur \cite{singh2022doh} proposed a hybrid approach combining feature selection with ensemble learning for DoH traffic classification, demonstrating that a reduced feature set could maintain high detection accuracy while reducing computational overhead.
    \item Zebari et al. \cite{zebari2023doh} applied deep learning architectures, including convolutional neural networks (CNNs) and long short-term memory (LSTM) networks, to the problem of encrypted DNS traffic analysis, achieving competitive results.
\end{itemize}

Despite the high accuracy reported in these studies, most existing solutions remain at the research stage and exhibit several common limitations:
\begin{itemize}
    \item They focus primarily on offline classification using pre-collected datasets rather than real-time packet capture.
    \item They lack integration with a deployable agent that can operate on endpoint devices.
    \item They do not provide a centralized management interface for monitoring and configuration.
    \item They do not incorporate network-level enforcement mechanisms such as firewall rules.
\end{itemize}

\subsection{Existing Security Solutions and Their Limitations}

Several commercial and open-source security tools address aspects of the DoH detection problem:

\textbf{Splunk} and \textbf{ELK Stack} provide powerful log analysis and SIEM capabilities but require significant configuration and lack native DoH-specific detection models. \textbf{Snort} and \textbf{Suricata} are network intrusion detection systems that can perform deep packet inspection, but their signature-based approach is ineffective against encrypted DoH traffic where the payload is not visible. \textbf{Wireshark} and \textbf{tcpdump} offer packet capture and analysis but are passive analysis tools without automated detection capabilities. \textbf{Cisco Umbrella} and \textbf{Cloudflare Gateway} provide DNS-layer security but operate as cloud services rather than endpoint agents and may introduce latency or privacy concerns.

The analysis of existing solutions reveals a gap in the market for a lightweight, open-source, endpoint-based DoH detection system with centralized management. ShieldX aims to fill this gap by providing an integrated solution that combines real-time packet capture, machine learning classification, and a web-based management dashboard.

\subsection{User and System Requirements Analysis}

The primary users of the ShieldX system are security administrators who need to monitor and protect endpoints in their network. The key requirements identified through analysis of the problem domain are as follows:

\begin{itemize}
    \item \textbf{Real-time detection}: The system must be capable of capturing and analyzing live network traffic to detect malicious DoH flows as they occur.
    \item \textbf{Accuracy}: The detection model must achieve high accuracy with low false-positive rates to avoid alert fatigue.
    \item \textbf{Centralized visibility}: Administrators must be able to view the status of all deployed agents, review malware alerts, and manage security policies from a single dashboard.
    \item \textbf{Network enforcement}: The system should be able to enforce domain whitelists at the network level, blocking traffic to unauthorized domains.
    \item \textbf{Cross-platform compatibility}: The agent should support both Linux and Windows endpoints.
    \item \textbf{Scalability}: The architecture should support multiple agents reporting to a single backend.
\end{itemize}

\subsection{Detailed Use Case Description}
\label{subsection:2.2.2}

\subsection{Business Process}
\label{subsection:2.2.3}

The core business process of the ShieldX system is the detection and response pipeline. The process begins with the agent capturing packets from the network interface. Packets are grouped into bidirectional flows, and 28 statistical features are extracted for each flow. The XGBoost model classifies the flow as benign or malicious. If malicious, an alert is sent to the backend, and the administrator can review the alert and take appropriate action, such as updating the whitelist or investigating the affected endpoint.

The complete business process is divided into three phases: agent initialization, the detection pipeline, and alert handling.

\subsubsection{Agent Initialization}

When the ShieldX agent starts, it first loads the pre-trained XGBoost model from disk, initializes the packet capture interface, and registers with the backend server via a heartbeat request. If the backend is unreachable, the heartbeat is queued for later retry. Once registration is confirmed, the detection pipeline scheduler begins.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.60\textwidth]{Figure/Chapter2/activity_init.png}
    \caption{Activity diagram of agent initialization}
    \label{fig:activity_init}
\end{figure}

\subsubsection{Detection Pipeline}

The detection pipeline runs continuously on a 120-second cycle. The agent captures packets from the network interface using a BPF filter for TCP traffic on port 443 (HTTPS). Captured packets are grouped into bidirectional flows based on the standard 5-tuple. Flows are marked as complete when either no packets have been observed for 40 seconds, or the flow has existed for more than 120 seconds. For each completed flow, 28 statistical features are computed covering bytes-level metrics, packet length distribution statistics, packet timing patterns, and response time analysis. The feature vector is then passed through a two-layer XGBoost classifier: Layer 1 distinguishes DoH from non-DoH traffic, and Layer 2 classifies DoH flows as benign or malicious.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.65\textwidth]{Figure/Chapter2/activity_detection.png}
    \caption{Activity diagram of the malware detection pipeline}
    \label{fig:activity_detection}
\end{figure}

\subsubsection{Alert Handling and Response}

When a malicious flow is detected, the agent extracts the flow details, logs them locally, and sends an alert to the ShieldX-web backend via a REST API call. If the backend is unreachable, the alert is queued for later retransmission. The security administrator can then log into the dashboard, review alerts, examine flow details, and decide whether to update the domain whitelist. Changes to the whitelist are propagated to agents during their next heartbeat cycle.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.55\textwidth]{Figure/Chapter2/activity_alert.png}
    \caption{Activity diagram of alert handling and administrator response}
    \label{fig:activity_alert}
\end{figure}

The process runs continuously, with the detection cycle repeating every 120 seconds and the heartbeat cycle every 60 seconds. The system is designed to operate autonomously, requiring administrator intervention only when malicious traffic is detected.

\section{Functional description}
\label{section:2.3}

\subsection{Description of use case ``Heartbeat Registration''}

\begin{itemize}
    \item \textbf{Use case name}: Heartbeat Registration
    \item \textbf{Primary actor}: ShieldX Agent
    \item \textbf{Precondition}: The agent is configured with the backend API URL and has network connectivity.
    \item \textbf{Flow of events}:
        \begin{enumerate}
            \item The agent sends a POST request to /heartbeat/ with agent identification and system information.
            \item The backend checks if the agent ID already exists in the database.
            \item If the agent exists, the backend updates the last\_seen timestamp and status to ``active''.
            \item If the agent is new, the backend creates a new agent record.
            \item The backend returns a success response.
        \end{enumerate}
    \item \textbf{Postcondition}: The agent is registered with an updated or newly created record in the database.
\end{itemize}

\subsection{Description of use case ``Malware Alert Reporting''}

\begin{itemize}
    \item \textbf{Use case name}: Malware Alert Reporting
    \item \textbf{Primary actor}: ShieldX Agent
    \item \textbf{Precondition}: The agent has detected a malicious flow via the ML classifier.
    \item \textbf{Flow of events}:
        \begin{enumerate}
            \item The agent extracts the 28 features from the malicious flow.
            \item The agent sends a POST request to /report-malware/ with agent ID, malware type, and flow details.
            \item The backend validates the agent ID and creates a new MalwareAlert record.
            \item The backend returns the created alert details.
        \end{enumerate}
    \item \textbf{Alternative flow}: If the agent ID is not found, the backend returns a 404 error.
    \item \textbf{Postcondition}: A new malware alert is stored in the database and visible on the dashboard.
\end{itemize}

\subsection{Description of use case ``Whitelist Domain Management''}

\begin{itemize}
    \item \textbf{Use case name}: Whitelist Domain Management
    \item \textbf{Primary actor}: Security Administrator
    \item \textbf{Precondition}: The administrator is logged into the ShieldX-web dashboard.
    \item \textbf{Main flow -- Add domain}:
        \begin{enumerate}
            \item The administrator navigates to the Whitelist page.
            \item The administrator clicks the ``Add Domain'' button.
            \item A modal dialog appears with fields for domain name and notes.
            \item The administrator enters the domain and clicks ``Add''.
            \item The backend validates the domain and creates a new WhitelistDomain record.
            \item The dashboard updates to show the new domain in the table.
        \end{enumerate}
    \item \textbf{Alternative flow}: If the domain already exists, the backend returns a 400 error.
    \item \textbf{Exception flow}: The administrator may edit or delete existing domains through similar modal dialogs.
    \item \textbf{Postcondition}: The whitelist is updated, and the change is propagated to agents on their next heartbeat.
\end{itemize}

\subsection{Description of use case ``Agent Status Monitoring''}

\begin{itemize}
    \item \textbf{Use case name}: Agent Status Monitoring
    \item \textbf{Primary actor}: Security Administrator
    \item \textbf{Precondition}: The administrator is logged into the ShieldX-web dashboard and at least one agent has registered with the backend.
    \item \textbf{Flow of events}:
        \begin{enumerate}
            \item The administrator navigates to the Agents page on the dashboard.
            \item The frontend sends a GET request to /api/v1/agents/ to retrieve all registered agents.
            \item The backend queries the database for all agent records and returns them as a JSON array.
            \item The dashboard renders an interactive table showing agent ID, hostname, IP address, status (active/offline), last seen timestamp, and uptime.
            \item Agents with a last\_seen timestamp older than 120 seconds are displayed with a red ``offline'' indicator.
            \item The table updates automatically every 30 seconds via a polling mechanism.
        \end{enumerate}
    \item \textbf{Alternative flow}: If no agents are registered, the dashboard displays an empty state with instructions for deploying the agent.
    \item \textbf{Postcondition}: The administrator has real-time visibility into all deployed agents and their operational status.
\end{itemize}

\subsection{Description of use case ``System Health Dashboard''}

\begin{itemize}
    \item \textbf{Use case name}: System Health Dashboard
    \item \textbf{Primary actor}: Security Administrator
    \item \textbf{Precondition}: The administrator is logged into the ShieldX-web dashboard.
    \item \textbf{Flow of events}:
        \begin{enumerate}
            \item The administrator navigates to the Dashboard page.
            \item The frontend sends parallel GET requests to multiple API endpoints to collect statistics: total agent count, active agent count, total alerts, alerts in the last 24 hours, and whitelist domain count.
            \item The backend aggregates and returns the statistics as a single response payload.
            \item The dashboard renders summary cards with count metrics, each with an icon and color-coded background.
            \item The administrator can click on each card to navigate to the corresponding detail page.
        \end{enumerate}
    \item \textbf{Postcondition}: The administrator has an at-a-glance overview of the entire ShieldX deployment's health and security posture.
\end{itemize}

\subsection{Description of use case ``Flow Detail Inspection''}

\begin{itemize}
    \item \textbf{Use case name}: Flow Detail Inspection
    \item \textbf{Primary actor}: Security Administrator
    \item \textbf{Precondition}: At least one malware alert has been reported to the backend by an agent.
    \item \textbf{Flow of events}:
        \begin{enumerate}
            \item The administrator navigates to the Malware Alerts page on the dashboard.
            \item The frontend sends a GET request to /api/v1/alerts/ with optional query parameters for filtering (date range, agent ID, malware type).
            \item The backend queries the MalwareAlert table with the applied filters and returns paginated results.
            \item The dashboard renders an interactive table with columns for timestamp, agent hostname, malware type, flow source/destination IPs, and confidence score.
            \item The administrator clicks on a specific alert row to expand its details, revealing the full 28-feature vector and packet-level metadata.
            \item The administrator can export the alert details as a JSON file for further analysis or integration with external SIEM tools.
        \end{enumerate}
    \item \textbf{Alternative flow}: If no alerts match the applied filters, an empty state message is displayed.
    \item \textbf{Postcondition}: The administrator has inspected the details of a specific malicious flow and can make informed decisions about further action.
\end{itemize}

\section{Hands-on Implementation Considerations}
\label{section:2.4}

Beyond the functional and non-functional requirements, several practical considerations inform the implementation of the ShieldX system:

\subsection{Packet Capture Requirements}

Real-time packet capture on endpoint devices requires careful consideration of operating system permissions and network interface characteristics:

\begin{itemize}
    \item \textbf{Root/Sudo Privileges}: Raw socket access for packet capture requires elevated privileges. The agent must be run as root or with CAP\_NET\_RAW capability on Linux.
    \item \textbf{Network Interface Selection}: The agent must allow configuration of the target network interface. On multi-homed systems, traffic may need to be monitored on multiple interfaces.
    \item \textbf{Packet Filtering Efficiency}: To reduce processing overhead, the agent uses BPF (Berkeley Packet Filter) expressions to capture only TCP traffic on port 443, discarding irrelevant packets at the kernel level before they reach the agent.
    \item \textbf{Buffer Management}: High-traffic environments may generate thousands of packets per second. The agent must implement efficient buffer management to avoid packet drops while maintaining classification throughput.
\end{itemize}

\subsection{ML Model Deployment Strategy}

Deploying a trained machine learning model on endpoint devices presents unique challenges:

\begin{itemize}
    \item \textbf{Model Portability}: The trained model must be serialized in a format that can be loaded on any endpoint regardless of the training environment. XGBoost's JSON format provides this portability.
    \item \textbf{Version Management}: As models are updated and improved, the agent must support model versioning and hot-swapping without requiring a full application restart.
    \item \textbf{Inference Latency}: The classification step must complete within milliseconds to avoid becoming a bottleneck in the detection pipeline. This requires efficient model evaluation optimized for the target hardware.
    \item \textbf{Memory Footprint}: The model must fit within the available memory of the endpoint device. Trees ensemble models can be compressed through pruning or quantization when necessary.
\end{itemize}

\subsection{Agent-Backend Communication Reliability}

The agent operates independently but relies on the backend for centralized management:

\begin{itemize}
    \item \textbf{Offline Resilience}: The agent must continue detection and local logging even when the backend is unreachable. Alerts should be queued locally and transmitted when connectivity is restored.
    \item \textbf{Heartbeat Mechanism}: Regular heartbeat signals indicate agent liveness. If no heartbeat is received within a configurable timeout, the backend should mark the agent as offline.
    \item \textbf{Idempotent Operations}: API operations should be designed to be idempotent, allowing the agent to retry failed requests without creating duplicate records.
    \item \textbf{Backpressure Handling}: If the backend is overwhelmed, it should signal the agent to reduce the alert frequency rather than dropping alerts.
\end{itemize}

\subsection{Security and Compliance}

The ShieldX system processes potentially sensitive network traffic data:

\begin{itemize}
    \item \textbf{Data Privacy}: The agent extracts only statistical features from network flows, not packet payloads. Statistical features cannot be reverse-engineered to recover original DNS queries, preserving user privacy.
    \item \textbf{Least Privilege}: The agent operates with the minimum necessary privileges: raw socket access for packet capture and root access for nftables management. The backend requires only database write access for alerts and read access for the whitelist.
    \item \textbf{Audit Trail}: All detection events are logged with timestamps and agent identification, providing a complete audit trail for security investigations.
    \item \textbf{Log Rotation}: The agent implements log rotation to prevent disk exhaustion during prolonged operation. Old log files are compressed and archived according to configurable retention policies.
\end{itemize}

\section{Non-functional requirement}
\label{section:2.5}

The following non-functional requirements guide the design and implementation of the ShieldX system:

\begin{itemize}
    \item \textbf{Performance}: The agent must process and classify network flows in near real-time. The capture-and-predict cycle should complete within 120 seconds to ensure timely detection. The ML model prediction for a single flow should complete in under 100 milliseconds.
    \item \textbf{Reliability}: The agent must operate continuously without crashing. In the event of a backend connectivity failure, the agent should continue local detection and queue alerts for later transmission.
    \item \textbf{Scalability}: The backend must support multiple agents (at least 50) reporting simultaneously. The API endpoints should respond within 500 milliseconds under normal load.
    \item \textbf{Usability}: The web dashboard should be intuitive and responsive, requiring minimal training for security administrators. The UI should follow standard design patterns with clear navigation and visual feedback.
    \item \textbf{Maintainability}: The codebase should follow modular design principles with clear separation of concerns. Each component should be independently testable and deployable.
    \item \textbf{Security}: The system must validate all inputs at the API layer. The agent should enforce network whitelisting at the kernel level using nftables. Communication between agents and the backend should be over HTTPS in production deployments.
    \item \textbf{Cross-platform}: The agent should be designed to support both Linux and Windows operating systems. The ML model should be portable and platform-independent.
\end{itemize}
