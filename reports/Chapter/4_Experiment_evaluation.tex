This chapter presents the complete design, implementation, and evaluation of the ShieldX system. It begins with the architectural design of the overall system, followed by detailed design of both the endpoint agent and the web dashboard. The implementation details, including the technologies used, achieved results, and user interface illustrations, are then presented. Finally, the testing methodology, experimental results, and deployment considerations are discussed.

\section{Architecture design}

\subsection{Software architecture selection}
\label{section:4.1.1}

The ShieldX system adopts a \textbf{two-tier client-server architecture} with elements of the \textbf{microservices} pattern. The architecture separates the system into two major components: the endpoint agent (ShieldX Agent) and the centralized management server (ShieldX-web). This separation provides several advantages:

\begin{itemize}
    \item \textbf{Scalability}: Multiple agents can be deployed across different endpoints, all reporting to a single backend server.
    \item \textbf{Independent deployment}: The agent and backend can be updated, tested, and deployed independently.
    \item \textbf{Centralized management}: Security administrators gain unified visibility into all agents through the web dashboard.
    \item \textbf{Fault isolation}: A failure in the backend does not affect agent operation (agents continue local detection and can queue alerts).
\end{itemize}

The agent follows a \textbf{pipeline architecture} internally, where packets flow through a sequence of processing stages: capture, flow assembly, feature extraction, classification, and alerting. The backend follows a \textbf{layered architecture} with separate layers for API routing, business logic, data access, and persistence.

\subsection{Overall design}
\label{section:4.1.2}

The system comprises the following packages, organized into distinct architectural tiers:

\begin{itemize}
    \item \textbf{shieldx-agent}: The endpoint agent package containing sub-packages for packet processing (packet\_processing), domain logic (domains), model inference (models), configuration (config), and the agent orchestrator.
    \item \textbf{shieldx-web-backend}: The FastAPI backend package containing sub-packages for API routes (api/v1/endpoints), service layer (services), data models (models), middleware (middleware), and utility functions (utils).
    \item \textbf{shieldx-web-frontend}: The React frontend package containing page components (pages), API client (api.ts), type definitions (types.ts), and theme configuration (theme.ts).
\end{itemize}

The ShieldX system is organized into multiple architectural layers, each with a distinct responsibility. The following subsections detail each layer's package structure and internal dependencies.

\subsubsection{Frontend Layer (ShieldX-web Dashboard)}

The frontend layer is a React single-page application (SPA) built with TypeScript and Chakra UI. It communicates with the backend exclusively through REST API calls via the Axios HTTP client. The layer is divided into four page components, a shared API client module, and TypeScript type definitions.

The frontend package (\texttt{shieldx-web-frontend}) follows a flat page-based structure: \texttt{pages/} contains four main views (Dashboard, Agents, MalwareAlerts, Whitelist), \texttt{api.ts} provides typed API functions via Axios, and \texttt{types.ts} defines TypeScript interfaces for the data models. The application is built with Vite and uses Chakra UI for responsive layout components.

\subsubsection{Backend Layer (ShieldX-web API)}

The backend layer implements a FastAPI REST API that follows a layered architecture pattern. The application factory in \texttt{app/main.py} configures middleware, registers routers, and manages the application lifecycle. Configuration is managed through Pydantic settings in \texttt{app/config.py}. The API layer (\texttt{api/v1/}) contains route handlers and dependency injection functions. The middleware layer provides request logging via a custom ASGI middleware. The models layer defines Pydantic schemas for request/response validation. The utils layer provides centralized logging configuration. The services layer contains reusable business logic, and the exceptions layer defines application-specific error types.

\subsubsection{Agent Core Layer (ShieldX Agent)}

The agent core layer is the heart of the ShieldX endpoint agent. It provides two execution modes: the full orchestrator (\texttt{agent\_orchestrator.py}) that integrates heartbeat, whitelist management, and detection; and the lightweight scheduler (\texttt{agent\_scheduler.py}) that runs only the detection pipeline on a timer.

The domain layer consists of three key modules: \texttt{pipeline.py} orchestrates the end-to-end detection flow (packet capture, feature extraction, ML inference), \texttt{firewall.py} manages nftables-based domain whitelist enforcement, and \texttt{system\_info.py} collects endpoint system information for agent registration. The logging configuration is centralized in \texttt{config/logging\_config.py}.

\subsubsection{Packet Processing Layer}

The packet processing layer is the most architecturally complex subsystem, responsible for transforming raw network packets into structured statistical features. It is organized into multiple sub-packages for separation of concerns.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.90\textwidth]{Figure/Chapter4/diagram_packet_processing.png}
    \caption{Packet processing layer: flow session management, flow objects, feature extractors, time-series analysis, and support modules}
    \label{fig:diagram_packet_processing}
\end{figure}

\texttt{flow\_session.py} defines a custom Scapy session that intercepts packets, groups them into bidirectional flows, and manages flow lifecycle (creation, update, expiration, garbage collection). \texttt{flow.py} represents a single flow and provides the \texttt{get\_data()} method that computes the 28 statistical features by delegating to four feature extractor classes: \texttt{FlowBytes}, \texttt{PacketLength}, \texttt{PacketTime}, and \texttt{ResponseTime}. The context sub-package (\texttt{features/context/}) provides foundational types such as \texttt{PacketDirection} and \texttt{PacketFlowKey} that are used across multiple feature extractors. The time-series sub-package provides an alternative clump-based flow representation for specialized analysis.

\subsubsection{ML Model Training Layer}

The model training layer is independent from the agent runtime and is used exclusively during development to train and evaluate the four machine learning models.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.80\textwidth]{Figure/Chapter4/diagram_ml_models.png}
    \caption{ML model training pipeline: from dataset preparation to trained model export and production deployment}
    \label{fig:diagram_ml_models}
\end{figure}

The training pipeline is orchestrated by \texttt{train\_all\_models.py}, which spawns each model training script as a separate subprocess. All four scripts (\texttt{random\_forest.py}, \texttt{lightgbm\_model.py}, \texttt{xgboost\_model.py}, \texttt{svm\_model.py}) share the same data preprocessing module (\texttt{preprocess.py}) for loading and preparing the CIC-DoHBrw-2020 dataset. The \texttt{merge\_and\_prepare.py} script handles initial data merging of benign and malicious CSV files.

The ShieldX system depends on a rich ecosystem of open-source libraries and frameworks that span packet manipulation, machine learning, web development, and system utilities.

The agent runtime dependencies (Scapy, XGBoost, NumPy, APScheduler) are kept minimal for lightweight deployment, while the training and backend dependencies (scikit-learn, FastAPI, Pydantic) are isolated in separate environments.

\subsection{Layer design}
\label{section:4.2.2}

The agent pipeline is designed as a sequence of processing stages, each encapsulated in a dedicated module:

\paragraph{Stage 1 -- Packet Capture:} The \texttt{AsyncSniffer} from Scapy captures packets from the network interface. It runs in a background thread and passes captured packets to the \texttt{FlowCollector} (a subclass of \texttt{FlowSession}) for processing.

\paragraph{Stage 2 -- Flow Assembly:} The \texttt{FlowCollector} groups captured packets into bidirectional flows. A flow is identified by the tuple (source IP, source port, destination IP, destination port). The \texttt{Flow} object maintains a list of packets with their direction annotations (FORWARD or REVERSE).

\paragraph{Stage 3 -- Feature Extraction:} When a flow expires (after 40 seconds of inactivity or exceeding 120 seconds duration), the \texttt{Flow.get\_data()} method computes the 28 statistical features from the stored packets.

\paragraph{Stage 4 -- Classification:} The feature vector is passed to the pre-trained XGBoost model, which returns a prediction (0 for benign, 1 for malicious). The model is loaded lazily and cached for subsequent predictions.

\paragraph{Stage 5 -- Alerting:} If the prediction is malicious, the agent sends a POST request to the backend's /report-malware/ endpoint with the flow details.

\subsection{Database design}
\label{section:4.2.3}

The system uses a MySQL database with three tables:

\paragraph{Agent table:} Stores information about each registered ShieldX agent, including its unique ID, hostname, IP address, first and last seen timestamps, and current status (active/offline).

\paragraph{MalwareAlert table:} Stores reports of detected malicious flows, with references to the reporting agent, malware type classification, detailed flow features, and detection timestamp.

\paragraph{WhitelistDomain table:} Stores the list of trusted domains that agents should allow traffic to. Each entry includes the domain name, optional notes, and the date added.

\subsection{Agent Testing}

The ShieldX agent includes a test suite using pytest and unittest.mock. The tests cover three core areas:

\paragraph{Model Loading and Prediction:}
\begin{itemize}
    \item \texttt{TestLoadModel}: Verifies that the XGBoost model loads correctly from the JSON file and that subsequent calls return the cached model without reloading.
    \item \texttt{TestPredict}: Tests prediction with dictionary input for both benign (prediction = 0) and malicious (prediction = 1) feature vectors. Also tests edge cases such as empty dictionaries.
    \item \texttt{TestFilterModelFeatures}: Verifies that fields not used by the model (SourceIP, SourcePort, DestinationIP, DestinationPort, Duration, TimeStamp, DoH) are correctly filtered out before prediction.
\end{itemize}

\paragraph{Pipeline Integration:}
\begin{itemize}
    \item \texttt{TestCaptureAndPredict}: Tests the full capture-and-predict pipeline with mocked packet capture. Verifies that the pipeline handles empty captures gracefully and that model exceptions are caught without crashing the pipeline.
    \item \texttt{TestFlowCollector}: Tests the custom flow collector, verifying that expired flows are garbage-collected and that the output file is set to /dev/null.
\end{itemize}

\subsection{Backend API Testing}

The backend includes API-level tests:
\begin{itemize}
    \item \texttt{test\_health.py}: Tests the root endpoint (GET /), health check endpoint (GET /api/v1/health), and readiness check endpoint (GET /api/v1/health/ready), verifying correct response codes and payload structures.
\end{itemize}

\section{Deployment}
\label{section:4.5}

The ShieldX system is deployed as follows:

\paragraph{Agent Deployment:} The ShieldX agent is installed on each endpoint to be monitored. The deployment requirements are:
\begin{itemize}
    \item Python 3.10+ runtime environment.
    \item Root/sudo privileges for packet capture (raw socket access) and nftables management.
    \item Network connectivity to the ShieldX-web backend server.
    \item The XGBoost model file (xgboost\_model.json) placed in the agent's working directory.
\end{itemize}

The agent can be started with the command \texttt{python -m src.main} for full orchestrator mode or \texttt{python -m src.agent\_scheduler} for lightweight scheduling mode.

\paragraph{Backend Deployment:} The ShieldX-web backend is deployed as a FastAPI application behind a reverse proxy (e.g., Nginx) for production use:
\begin{itemize}
    \item MySQL 8.0 database (can be run via Docker as provided in docker-compose.yml).
    \item Environment variables configured for database URL, host, port, and log level.
    \item The backend is started with \texttt{uvicorn main:app --host 0.0.0.0 --port 8000}.
\end{itemize}

\paragraph{Frontend Deployment:} The React frontend is built into static files and served via a web server (Nginx or similar):
\begin{itemize}
    \item Build command: \texttt{npm run build} (output in dist/ directory).
    \item The built files can be served by any static file server.
    \item The API base URL is configured via the VITE\_API\_URL environment variable.
\end{itemize}

\section{Model Comparison and Evaluation}
\label{section:4.6}

While the ShieldX production agent uses XGBoost as its primary classifier, four different machine learning models were trained and evaluated on the CIC-DoHBrw-2020 dataset to identify the most suitable algorithm for real-time DoH traffic classification. This section presents a comprehensive comparison of Random Forest, LightGBM, XGBoost, and Support Vector Machine (SVM) classifiers.

\subsection{Experimental Setup}
\label{section:4.6.1}

All models were evaluated under identical conditions to ensure a fair comparison:

\begin{itemize}
    \item \textbf{Dataset}: CIC-DoHBrw-2020 with 499,106 labeled network flows (28 statistical features).
    \item \textbf{Train/Test Split}: 80/20 stratified split with random\_state=42, yielding 399,284 training samples and 99,822 test samples.
    \item \textbf{Evaluation Metrics}: Accuracy, Precision, Recall, F1-Score (Malicious class), ROC-AUC, False Positive Rate (FPR), model size, and inference time.
    \item \textbf{Hardware}: All models were trained and evaluated on the same workstation to ensure consistent timing measurements.
\end{itemize}

\subsection{Model Configuration}
\label{section:4.6.2}

Each model was configured with hyperparameters that balance classification performance with computational efficiency:

\begin{itemize}
    \item \textbf{Random Forest}: 100 decision trees (n\_estimators=100), random\_state=42, n\_jobs=2. Random Forest builds an ensemble of decision trees on bootstrapped training samples and averages their predictions. It is known for its robustness against overfitting and ability to handle high-dimensional feature spaces.
    \item \textbf{LightGBM}: 100 boosting iterations (n\_estimators=100), random\_state=42, n\_jobs=-1, with early stopping (patience=10 rounds) based on validation log-loss. LightGBM is a gradient boosting framework that uses leaf-wise tree growth, which often results in faster training and lower memory usage compared to level-wise growth.
    \item \textbf{XGBoost}: 200 trees (n\_estimators=200), max\_depth=6, random\_state=42. XGBoost (Extreme Gradient Boosting) implements regularized gradient boosting with L1 and L2 regularization, handling missing values automatically and supporting efficient parallel computation.
    \item \textbf{SVM}: Radial Basis Function (RBF) kernel, C=1, max\_iter=1000. SVM finds the optimal hyperplane that maximizes the margin between classes in a transformed feature space. The RBF kernel enables non-linear decision boundaries.
\end{itemize}

\subsection{Computational Efficiency}
\label{section:4.6.5}

For real-time deployment on endpoint devices, model size and inference speed are critical considerations:

\begin{itemize}
    \item \textbf{Random Forest}: The largest model at 8,027 KB due to storing all 100 decision trees explicitly. Inference time is moderate at 0.60 seconds for the full test set (approximately 6 microseconds per sample).
    \item \textbf{LightGBM}: The most compact model at only 96 KB, achieved through LightGBM's efficient histogram-based tree representation. Inference is slightly slower (1.11 seconds for the test set) due to leaf-wise tree traversal.
    \item \textbf{XGBoost}: A balanced choice at 328 KB with the fastest inference time (0.29 seconds for the full test set, approximately 2.9 microseconds per sample). XGBoost's level-wise tree growth enables efficient SIMD-optimized evaluation.
    \item \textbf{SVM}: Moderate size at 479 KB but the slowest inference (17.24 seconds for the test set, approximately 173 microseconds per sample) due to the kernel computation required for each prediction.
\end{itemize}

\subsection{Discussion and Model Selection}
\label{section:4.6.6}

The experimental results demonstrate that tree-based ensemble methods significantly outperform SVM for the task of DoH traffic classification using statistical flow features. All three tree-based models achieve accuracy exceeding 99.99\%, confirming that the 28 statistical features provide highly discriminative information for distinguishing benign from malicious encrypted traffic.

XGBoost was selected as the production model for ShieldX based on the following rationale:

\begin{itemize}
    \item \textbf{Best overall accuracy}: XGBoost achieves 100.00\% accuracy (rounded to four decimal places) with only 5 total misclassifications across 99,822 test samples.
    \item \textbf{Fastest inference}: At 2.9 microseconds per sample, XGBoost is the most suitable for real-time classification on resource-constrained endpoints.
    \item \textbf{Compact model size}: 328 KB is easily deployable and fits in device memory without issue.
    \item \textbf{Proven reliability}: XGBoost has been widely adopted in both academic research and industrial applications for tabular data classification.
\end{itemize}

The near-perfect results also suggest that the CIC-DoHBrw-2020 dataset, while comprehensive, may contain inherent patterns that are relatively easy for tree-based models to exploit. Future work should explore cross-dataset validation to assess generalization to unseen DoH traffic patterns.

\subsection{Feature Importance Analysis}
